01 / THE BRIEF

You’re the security reviewer.

A fictional organization has built a service for its internal documents. Employees sign in, read and download documents, and edit them when they have permission. The maintenance team has also prepared a backup.

You are the security specialist asked to review the service before handover. Find and fix the problems. Investigate which documents each person can access, who can retrieve the backup, and what the server records about their activity.

First test the service you have been given. Then change the code or configuration, and repeat those tests to show what your changes actually achieved.

At the end, hand over the corrected project, your tests, their results, and a short report.

§Organization security policyINTERNAL DOCUMENT · SEVEN RULES＋
THE ORGANIZATION
Information Security OfficeINTERNAL
POLICY

DOCUMENT SEC–01 / ACCESS, BACKUPS & AUDIT

Rules for the document service

These are the rules the service is expected to follow. Your experiments establish how well the delivered version actually follows them.

A

Sign-in comes first

A person who has not signed in must not receive the document list, document content, or a document download, or change a document.

B

Employees

Employees may read and download documents in their own department. They may edit only documents they created.

C

Department managers

Managers may read, download, and edit documents in their own department. They have no access to the other department’s documents.

D

Every way of accessing a document

The same rules apply to the web interface and to requests sent directly with tools such as curl.

E

The backup

Neither unsigned-in visitors nor signed-in employees or managers may retrieve the backup through network requests available to web users. The maintenance tool must still be able to retrieve and check it.

F

Server logs

For every document read, download, or edit request, record the time, the username used to send it, the requested document ID, the requested action, and the result. Include denied requests and requests for IDs that do not exist. Never store passwords, tokens, the Authorization header value, or document text in the log. For denied requests, do not log the document’s title, owner, or department either.

G

Keep legitimate work working

Authorized operations must continue to work after your fixes. If an edit request is denied, the document’s text must remain unchanged.

END OF POLICY · RETAIN FOR YOUR SECURITY REVIEW
i
A request can be sent without permission.

Someone who has not signed in can still ask to read a document. The server must reject the request and record anonymous instead of a username. Server logs are messages written by the application; the HTTP inspector in the interface shows requests and responses from that browser page.

After sign-in, the server returns a string called a token. Sending it with later requests identifies the signed-in account. It travels in a request header called Authorization. The interface handles this for you; with curl, you include it yourself.

THE HANDS-ON WORK

Six steps to a defensible handover.

Complete Tasks 1–4 on the original version and save the results. Make your fixes in Task 5. For every test, identify the account used, the request sent, the expected behavior under the policy, and what actually happened.

Open a hint when you need a starting point. Choosing tests, finding the cause, and designing the fix are your work.

01
GET ORIENTED

Take delivery of the service.

＋

Start the environment and pass the readiness check. Open http://127.0.0.1:8080/, sign in as Sara, and read and download a document. Use the HTTP inspector to see the request and response behind each action. Also sign in with curl and retrieve the list of Engineering documents.

SAVE THIS

The successful readiness-check output, the document-list request sent as sara, and the server’s response. This checks readiness; you will assess access rules in the following tasks.

↳ Need a starting point? Setup & your first request＋

Extract the package and open a terminal in the directory containing compose.yaml:

BASH / SETUP
docker compose version
docker compose up -d --build --wait
python3 tests/smoke.py

If startup fails, inspect docker compose ps and docker compose logs --no-color app. The interface starts in English and also offers Persian.

Sign in, then use the returned token to request the document list:

BASH / SIGN IN & LIST
curl --noproxy '*' -sS -H 'Content-Type: application/json' \
  -d '{"username":"sara","password":"s1"}' \
  http://127.0.0.1:8080/login

TOKEN='the token from the sign-in response'
curl --noproxy '*' -i -H "Authorization: Bearer $TOKEN" \
  http://127.0.0.1:8080/docs

documents is the list of documents the application returns. Sara belongs to Engineering, so the policy allows her to see documents 1, 2, and 3.

Examples use Bash. If you use a different shell, give a chatbot the command and your shell’s name and ask for an appropriate version. Sign in again after restarting the server to obtain a fresh token.

02
TEST THE POLICY

Put document permissions to the test.

＋

Design experiments for the document rules. Using an employee account, try reading, downloading, and editing their own document, a colleague’s document in the same department, and a document from the other department. Repeat with a manager account. Use accounts from both departments and send requests without signing in. Check that each person receives only their department’s document list, and that an unsigned-in visitor receives none.

Pass at least one signed-in request through ZAP, inspect it, and replay it. Keep the main tests as curl requests or scripts so you can repeat them after fixing the service.

SAVE THIS

For each test: the request, the account used, the response expected under the policy, and the actual response. Keep one ZAP observation or replay. For edits, compare the text before and after using an account allowed to read the document.

↳ Need a starting point? From a rule to an experiment＋

Ask: “If I send the same request as someone else, select a different document ID, or request an edit instead of a read, what should happen under the policy?” Establish the expectation before inspecting the actual response. The HTTP reference is at the end of this page.

An error status alone does not show that the data stayed unchanged. Successful authorized requests also matter: they establish that the service has not simply blocked everything.

In ZAP, configure the local proxy at 127.0.0.1:8090; the application uses port 8080. Route a normal request through the proxy:

BASH / THROUGH ZAP
curl --noproxy '' --proxy http://127.0.0.1:8090 \
  -H "Authorization: Bearer $TOKEN" http://127.0.0.1:8080/docs

Find it in History and resend it with Requester or Manual Request Editor. Menu names may vary. You can also sign in through a browser launched by ZAP. If the request is missing, check the proxy address and --noproxy '' so local traffic passes through ZAP. Active Scan is not required; base your explanation on actual requests and responses.

03
FOLLOW THE DATA

Check the backup from both sides.

＋

The maintenance team says, “We have a backup, but application users are not supposed to take it.” Before making fixes, check the two parts of that claim separately:

  1. From your computer’s terminal, scan the allowed ports with Nmap. Then use a browser or curl to investigate whether the backup can be retrieved through routes available to web users. Do not use docker exec or join the maintenance network for this test.
  2. From a terminal in the project directory, run the existing maintenance tool with docker compose run --rm ops and inspect its result.
SAVE THIS

The Nmap output, requests and responses from your backup-retrieval attempts, and the maintenance tool’s output. If you retrieve a file, check for documents inside it and record the result. An open port alone does not prove retrieval.

↳ Need a starting point? Two routes, two questions＋
BASH / LOCAL DISCOVERY
nmap -sT -Pn -n -p 8080-8083 127.0.0.1

A port is an entry point to a service. Use the scan and project configuration to identify services, then send requests to discover what they return. compose.yaml describes network connections, published ports, and data locations.

i
What does ops actually do?

ops tests whether the backup is usable. It runs separately from web accounts, retrieves the backup through the maintenance route, makes a temporary copy, opens it, and checks the database and expected documents. It then removes that copy. Your current application documents and edits remain untouched.

The backup contains the initial documents; later edits are not added. Success includes "restore": "ok", "rows": 5, and "sample_id": 4: the file was checked, it contained five documents, and sample document 4 was checked. You do not need to write a new recovery tool.

Use the ops result to assess maintenance access. Use the browser or curl results from the first test to assess web-user access.

04
EXAMINE THE EVIDENCE

Inspect the server logs.

＋

Send several read, download, and edit requests: some using accounts permitted to act, others using accounts without permission. Also send a request without signing in and one for an ID that has no document. Find the corresponding server-log lines.

Can you identify which account sent each request, the document requested, whether the server performed or denied the action, and when it happened? Does the log contain a password, token, document text, or document details forbidden by Policy F?

SAVE THIS

Your requests and their corresponding log lines. Identify exactly which required details are missing—for example, the username or document ID. Identify any password, token, or document text that was logged. If nothing was recorded for a request, keep its send time and the relevant time window of the log.

↳ Need a starting point? Match requests to log entries＋
BASH / SERVER LOGS
docker compose logs --no-color app

Send requests one at a time so their log lines are easy to locate. You may choose the log format. Include a timezone, such as UTC, in timestamps. Use read, download, and edit or briefly explain equivalent action names.

Record the document ID supplied in the request. When a request is denied, do not include the document title, creator, department, or text. To test for content leakage, put a distinctive test string in a document you may edit, send requests, and search the logs for that string.

Use server logs to investigate curl and ZAP requests. The interface’s HTTP inspector shows only requests from that page. Its JSON export redacts document text; save a read response separately when you need a before-and-after comparison.

05
HARDEN & VERIFY

Make the fixes. Repeat the tests.

＋

Use your observations to locate the causes in code or configuration and fix them. Repeat Tasks 2–4. Unauthorized requests should be denied, authorized requests should succeed, and a denied edit should leave the original text unchanged. Web users must not retrieve the backup; ops must still retrieve and check it. Compare the final logs with Policy F.

Keep the accounts, initial data, request paths, service names app, backup, and ops, and network names users and maintenance. You may change code and access configuration. Disabling features or replacing the backup check with a success message does not complete the mission.

SAVE THIS

The corrected project and rerun results, including another Nmap scan and ops run. For each issue, demonstrate that a previously successful policy violation is now denied while at least one related authorized operation still works. Reset the data and repeat the tests before handing over.

REFERENCE / HTTP

The requests you’ll work with.

APIOpen the HTTP referenceENDPOINTS · RESPONSES · MAINTENANCE ROUTE＋

Base URL: http://127.0.0.1:8080. For document routes, send Authorization: Bearer TOKEN, replacing TOKEN with the sign-in response’s token. Omit the header to test an unsigned-in request. Replace {id} with a numeric document ID, such as /docs/1.

RequestInput or successful response
GET /healthService readiness; no sign-in required.
POST /loginJSON input: username, password. Response includes token, username, unit, role.
GET /docsA documents list; each entry includes id, unit, owner, title.
GET /docs/{id}Document details and text in content.
GET /docs/{id}/downloadDocument text as text/plain.
PUT /docs/{id}JSON input such as {"content":"new text"}. Response includes id and the new content.

GET retrieves data; POST /login signs in; PUT changes content. Send sign-in and edit data as JSON with Content-Type: application/json.

200

Successful operation.

401 / 403 / 404

Accepted for denied unsigned-in requests.

403 / 404

Accepted for a signed-in account without permission.

You may use 404 to conceal a document’s existence. A denied response must not return document details or text. Authorized edits with less than 8 KB of text must be supported.

The internal backup endpoint

The maintenance tool retrieves http://backup:8081/backup.sqlite inside Docker’s network; backup is the service name. The checking code is in app/restore.py. It checks the SQLite database, the document count, and document 4’s text against FIN-OMID-SEED: fictional budget 75000 credits.. The output’s sha256 is a digest identifying the retrieved file.
